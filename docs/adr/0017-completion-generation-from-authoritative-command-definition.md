# ADR-0017: Completion generation from authoritative command definition

- **Status:** accepted
- **Date:** 2026-08-11
- **Decision-makers:** architect

## Context and Problem Statement

Shell users need completion scripts for the CLI command tree. Hand-maintained
scripts can drift from the options, positional argument, subcommands, and value
choices that Clap actually parses. Completion generation must also be safe for
first-run and scripted use: it must not create configuration, resolve a
provider, contact a service, write shell files, or contaminate stdout/stderr
with unrelated diagnostics.

The completion library exposes a broader shell enum than the product supports.
How should watn generate Bash, Elvish, Fish, PowerShell, and Zsh scripts while keeping the public
selector closed and the unsupported-shell error stable?

## Decision Drivers

- Keep completion metadata aligned with the command definition used by parsing
  and help.
- Support exactly Bash, Elvish, Fish, PowerShell, and Zsh through lowercase command-line values.
- Keep unsupported-shell guidance literal and actionable.
- Preserve stdout-only, deterministic, parser-accepted output for scripting.
- Bypass configuration, provider, network, file, and shell-startup side effects.
- Make the reserved `completions` command token an explicit CLI consequence.

## Considered Options

- **Maintain separate completion scripts** - simple to inspect, but every option,
  subcommand, and value change can make the scripts stale.
- **Expose `clap_complete::Shell` directly** - minimizes mapping code, but accepts
  shells outside the product contract and couples the public error surface to a
  library enum.
- **Use a local closed selector with `Cli::command()`** - requires an explicit
  mapping at the renderer boundary, but keeps the selector and metadata under
  product control.
- **Generate completion files or install them automatically** - convenient for
  some callers, but introduces filesystem and shell-configuration side effects
  that do not belong in a CLI output command.

## Decision Outcome

Choose a local `CompletionShell` selector with exactly the lowercase values
`bash`, `elvish`, `fish`, `powershell`, and `zsh`, matching all native generators
in the pinned `clap_complete` release. Unsupported values are rejected by the local parser
with the literal contract
`unsupported shell '<value>'; choose bash, elvish, fish, powershell, or zsh`, embedded in the
normal non-zero CLI argument error. The broader `clap_complete::Shell` type is
used only behind the renderer mapping and is not exposed as the CLI argument
type.

The generator obtains the command metadata from `Cli::command()`, then maps the
validated selector to the corresponding Bash, Elvish, Fish, PowerShell, or Zsh renderer and writes
the script directly to stdout. The completion branch returns before config
loading, config auto-init, provider resolution, model discovery, network access,
or spinner setup. It writes no file or shell startup configuration and emits no
stderr on success. The same binary and selector must produce byte-for-byte
identical output, and the regular scenarios pass each script through its target
shell parser.

Adding the `completions` subcommand reserves an unquoted first token
`completions`. A question whose first token is that word must be quoted as one
argument or passed after `--`.

## Consequences

### Good

- Generated options, positional arguments, subcommands, and selector values
  follow the authoritative Clap command definition.
- The closed selector prevents unsupported library values from becoming product
  behavior and keeps error guidance stable.
- Direct stdout generation is suitable for install/source workflows and does not
  mutate configuration, provider state, shell startup files, or the filesystem.
- Deterministic output and shell-parser checks make generated scripts observable
  and suitable for regression tests.
- The no-config scenario can prove that first-run auto-init and provider access
  are bypassed rather than merely absent from a fixture.

### Bad

- Supporting another shell requires changing the local selector, renderer map,
  help contract, and feature coverage.
- The project depends on the completion library's renderer output and must keep
  its version compatible with Clap; renderer changes may alter generated bytes.
- Shell parser availability and syntax behavior differ across environments, so
  local verification can fail when a supported shell executable is missing.
- The reserved `completions` token changes how an unquoted question beginning
  with that token is parsed.

## Confirmation

The completion feature covers all root options, the `question` positional
argument, root subcommands, and `bash`/`zsh`/`fish` selector suggestions for
each supported shell. It also verifies stdout-only success, empty stderr,
byte-for-byte determinism, target-shell parser acceptance, the literal
unsupported-shell contract, explicit help, and the before/after no-config and
provider-sentinel snapshots. The exact verification wrappers remain
`./run-tests.sh` and `./run-tests.sh --e2e`; `givn lint --change
shell-completions` and `git diff --check` are required before archival.
